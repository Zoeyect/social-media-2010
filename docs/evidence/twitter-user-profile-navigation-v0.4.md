# iOS 4.1 Twitter User Profile Navigation v0.4 Evidence

## Scope

- Twitter-local feature only.
- Restore navigation from tweet metadata into a reusable user profile view.
- Preserve all existing runtime contracts, foundation systems, scheduler behavior, and cross-app timeline ownership.

## Data Model

| Item | Value / Status |
| --- | --- |
| Twitter profile view states | `timeline`, `tweetDetail`, `userProfile`, `composer`, `secondaryTab` (app-local) |
| New profile fields | `selectedUserId`, `profileOriginView` in `TwitterState` |
| Profile record type | `TwitterUserProfile` records maintained in `twitterState.ts` |

### Profile record source

- Curated local fixtures for known fictional users (`June`, `Nora`, `Mia`, `Eli`, `Sam`) with minimal, plausible metadata.
- Session owner profile rendered as derived identity view (avatar seed + handle from `twitterReplyHandle`) when opened.
- Public figures currently include minimal metadata and `statsHold` flags where exact 2010 counts are not considered verified.

## READY / HOLD Classification

### READY

- Profile entry points from:
  - timeline avatar
  - display name
  - author handle
- Distinct tap destinations:
  - timeline tweet cell still opens tweet detail
  - profile links only open profile view
- Profile back routing:
  - from timeline-origin: return to timeline
  - from detail-origin: return to tweet detail
- Profile state survives app suspension/switching because it is entirely in `TwitterState`.
- New session reset clears `selectedUserId` and returns timeline baseline.
- No scheduler entries are generated by profile navigation.
- No cross-app/system state changes were introduced.

### HOLD

- Exact historical avatar bitmaps for named/public users (dev initials placeholders are used where no verified portrait is available).
- Exact period-verified biography wording and profile-action chrome.
- Cover-photo / tab set / follow/block/report interactions.
- Exact verified location of every public figure profile and exact follower/following/tweet/favorite counts when unavailable in evidence.

## Behavior Observed (Implementation)

1. **Entry point**
   - `OPEN_USER_PROFILE` action with `displayName` and `originView` opens `currentView = "userProfile"`.
2. **Profile content**
   - Header: display name, handle, optional verified marker, bio/location/web metadata when present.
   - Statistics rows shown using `formatProfileCount` (non-existent values render as `—`).
3. **Back behavior**
   - `BACK_FROM_PROFILE` checks stored `profileOriginView`.
4. **Origin preservation**
   - Opening profile from tweet detail preserves detail state while profile is active.
   - Opening profile from timeline preserves timeline state and scroll container anchor behavior.
5. **Non-invasive constraints**
   - No changes to lock notification routing.
   - No changes to timer/scheduler/cross-app timeline.
   - No changes to battery, Messages, Device Foundation, camera, or sibling apps.

## Risks / Remaining Items

- No evidence-ready historical fixture set for all named public figures/fictional users.
- Profile action controls are intentionally read-only in v0.4 pending explicit 2010 interaction audit.
